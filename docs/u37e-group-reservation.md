# U-37E – Samlet ordredatabase og reservasjon
Implementert ren validerings- og planleggingskode (ikke tilkoblet ordre-API). Krever eksplisitt vilkårsaksept, request-ID, forventet serverpris-digest og ny serverberegning. Fjerner klientpris og klientidentitet. Deler hver leielinje i én rad per fysisk enhet med eksakt beløp; stabil sortering av låserekkefølge; idempotensmodell knyttet til kunde, request-ID og prisgrunnlag. Digest alene er ikke autentisering eller bevis for samtykke. Ingen ekte ordrenummer.
SQL-utkast definerer gruppe med unik ordrenummersekvens, kunde/request unikhet, leie-/vare-/depositumbeløp, snapshot, status, bookingbarn, varelinjer, reserverte enheter og hendelser. RLS og ingen tilgang for klient eller service_role på nye tabeller i utkastet. Utkast ruller tilbake; erstatter U-37C schemautkast. Ingen migrasjon kjørt.
## Neste: implementere og teste faktisk transaksjon
1. Krev verifisert innlogget kunde i første versjon (gjest og bedriftskreditt senere). Request-ID bindes til bruker og eksakt innhold. Eksakt replay returnerer opprinnelig gruppe, konflikt avvises. Ordrenummer er unik sekvens, ikke fakturanummer; hull etter rollback er tillatt.
2. I samme DB-transaksjon lås request og alle rental_items med samme pg_advisory_xact_lock(hashtext(item_id::text)) som enkeltbooking, deretter radlåser i stabil rekkefølge; lås salgsvarer. Revalider serverpriser, vilkår, dato/Oslo, buffer, kapasitet, manuelle blokker, forsinket retur og stock_quantity-reserved_quantity. Ikke stol på gammel quote. Bruk samme prisformel/avrunding som JS med parity-tests.
3. Eksisterende bookingfunksjon i 20261025190000_private_rental_checkout_hold.sql bruker per-item lock, teller én rad per enhet og utløper enkelte gamle holds. Før gruppeinnføring må alle writers og lesere gjennomgås: admin bookinger/blokker/maintenance/manual-booking, kundens enkeltbetaling, betalingslenke, Vipps webhook/status, påminnelser, kalender, kundeside og accounting/kvittering. U-08 blokkguard er et utkast, og overdue-funksjonen er app-side. Ikke la gruppebarn utløpe, betales, faktureres eller endres enkeltvis. Ensartet transaksjonssperre for gamle og nye writers er en forutsetning.
4. Opprett alle bookingbarn, varelinjer, gruppe og reserverte varer i én transaksjon; feil ruller tilbake alt. Bruk private serverkall; ingen offentlig tabelltilgang. Gruppering må være synlig i admin og kundeportal. Oppdater quote/low-stock/admin til tilgjengelig beholdning. Ordrebaserte lagerhendelser må bli synlige i historikk. 
5. Frigivelse, signatur, betalingsstart, capture, sen betaling og utlevering er separate, låste og idempotente gruppeoverganger. Ingen automatisk frigivelse av betalingsforsøk uten leverandøravklaring. Én samlet Vipps-referanse, separat depositum, én signert avtale. Ingen betaling før transaksjon og signeringsflyt er godkjent.
6. Isolert PostgreSQL-test: to kunder om siste maskin/vare, enkeltbooking mot gruppe, manuell blokk mot gruppe, feil på siste vare, replay og konflikt, utløp mot capture, prisendring, negative mengder, forsinket retur, tilgangstest for annen kunde. Først deretter migrasjon og feature flag. Ingen produksjonsendring.
