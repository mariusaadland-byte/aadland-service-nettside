# U-38D – Transaksjonskandidat for signeringsarkiv
Utvider U-38B SQL-utkast, ruller tilbake, ingen runtime-grants. Konto-lås, gruppelås og challenge-radlås; sjekk gjeldende versjon, kunde, auth-bekreftet e-post, frosset pris og reservasjonsfrist. Kompositt-FK for gjeldende dokument. Utstedelsesgrense 3/time, 60 sekunder, feilforsøk 5/time på tvers av avtaler og maks 5 per challenge. Ny kode revokerer tidligere kode; feil lagres før avvisningssvar. Revoke avgrenset til eksakt pending ID. Koden slettes (MAC null) ved utløp, revokering, låsing eller signering. Unikt bevis per avtale.
Node-plan utfører eksisterende HMAC-kontroll, bygger server-only CAS-parametere. SQL sjekker samme MAC, forsøk, nøkkel-ID, dokumentbinding og gjeldende kontekst under lås. Lagrer eksakt evidence_text og seal og forbruker koden i samme transaksjon. Ingen klartekstkode i RPC. SQL verifiserer IKKE selv HMAC eller signaturens kryptografiske bevis; må aldri gi klient tilgang, og betrodd server må verifisere på nytt ved stale. Ikke godta beslutning eller MAC fra klient. Samtidig resend/verify må testes; ved stale skal server lese på nytt og gjenta verifisering begrenset, ikke returnere suksess uten committed signed. Konto/IP-rate limit ved API, låsing av alle current-pointer writers og auth-endringer, nøkkelrotasjon, arkivgrants og retention gjenstår. 
Ingen SQL kjørt. Ingen live endpoint, ekte e-post, signert avtale eller produksjonsendring. Byggtest dekker JS og statisk struktur, ikke PostgreSQL. Før staging: syntetisk schema med U-37F og U-38B, test to sesjoner (issue/issue, issue/verify, verify/verify, wrong/wrong, expiry/verify, revision/verify), quota, rollback og fremmed bruker; sjekk auth/permissions, gamle writers og DB-rådgivere. Kundens PDF og bevis skal leveres via autorisert Min side; signeringsbekreftelse sendes bare etter committed signatur. Juridisk/personvernkontroll før live.
