# U-37F – Samlet transaksjon og utløp (isolert SQL-kandidat)
SQL-utkastet utvider U-37E og ruller tilbake. Inneholder to faktiske PL/pgSQL-funksjonskandidater for samlet reservasjon og frigivelse av aldri-startede, utløpte holds. Ikke en produksjonsmigrasjon. Ingen runtime-grants, API eller cron er tilkoblet. Forutsetter U-37 A/B tabeller og eksisterende rental_bookings schema. Eneste autoriserte fremtidige inngang er verifisert server; digest og snapshot må være generert fra samme aksepterte innhold og kunde, ikke direkte fra klienten. SQL sammenligner snapshot mot databasepriser og vilkår, men verifiserer ikke SHA-256 selv.
Reserve: request-lås per kunde, eksakt replay eller konflikt, lås rental_items med eksisterende per-item advisory lock, radlås, sjekk dager/Oslo, buffer, blokk, peak inkl forsinket retur, priser inkl helg/uke/langtid og samlet øre, deretter lås salgsvarer og sjekk tilgjengelighet. Alt opprettes i én transaksjon, én bookingrad per fysisk enhet; gruppens egne barn har ingen individuell betalingsfrist. Beholdning reserveres, ikke fysisk trukket. Ordrenummer sekvens, ikke fakturanummer.
Expiry: 30 minutter, gruppelås, ingen betalingsreferanse/start-event, sjekk barn og antall, frigjør reserverte varer og kanseller alle barn atomisk. Betaling som er startet/ukjent holdes. Ny betalingsstart må låse samme grupperad og skrive start før eksternt kall. Gjentatt utløp gjør ingen endring. Ingen automatisk refusjon, delretur eller faktisk betaling.
VIKTIG før noen aktivering: gjennomgå og endre ALLE gamle writers og lesere (enkeltbooking, betalingslink, Vipps webhook/status, admin/blocks/maintenance, påminnelser, utløp, kundeportal, kvittering). U-08 blokkguard og overdue i eksisterende booking-RPC må fullføres. Prisavrunding SQL numeric vs JS må testes for parity, barnas price_snapshot/kontaktfelt må tilpasses faktiske eksisterende konsumenter. Utløpsfunksjon må også avstemme full varelinje-snapshot og alle økonomiske avviksfelt, og det må finnes audit for ordrebevegelser. Test med syntetiske data og to samtidige DB-sesjoner (siste vare/maskin, legacy vs gruppe, block vs gruppe, rollback ved feil siste vare, replay, utløp mot betalingsstart, prisendringer, RLS/grants). Testfilen kjører bare JS-beslutningslogikk og statisk SQL-kontroll, ikke en DB-test. Ingen lokal Postgres bekreftet; ingen SQL kjørt eller live endret.
